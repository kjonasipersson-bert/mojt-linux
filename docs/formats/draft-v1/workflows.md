# Request-to-boot workflow formats

2026-11-01 review draft. The owner approved progressing the declarative plus
interactive request model; exact TOML/wire fields remain proposals. This extends
the [first format slice](README.md), without new MPM/MBT commands or changes to
deployed records. MBT syntax is deliberately deferred.

| Part | Specification | New record families |
| --- | --- | --- |
| User wishes and origins | [Configuration and wishes](configuration-wishes.md) | Request state, resolution lock; parsed TOML document shape |
| Metadata and bytes | [Sources/acquisition/cache](sources-cache.md) | Source, accepted snapshot, acquisition map, cache verification record |
| Exact authorized work | [Saved plans](saved-plans.md) | Execution plan and protected local approval |
| Complete next boot | [Generalized boot v2](boot-deployment-v2.md) | Boot inputs, initramfs binding, deployment, selection/request roots |

All thirteen record shapes plus the parsed configuration shape are closed
definitions in [workflow-formats.schema.json](workflow-formats.schema.json).
Common ID/encoding/limits remain unchanged. Opaque provider configuration/identity
needs the named adapter's versioned validation. Schema match is not authorization.

Desired policy, exact resolution, retained bytes, effective selection and actual
running state remain separate. Configuration and interactive roots coexist;
dependencies/recovery/build references are retention reasons, not one origin
flag. Removing a configuration claim never removes another explicit wish or
persistent interactive override.

Plans bind snapshots and exact executor/target inputs. Metadata refresh alone
does not change installed content or invalidate every locked snapshot. Approval
is protected target/scope/plan-bound evidence, not a hash that grants root.
Construction precedes finalized selection when generated bytes are unknown.
Ports keeps one profile/state/history commit; boot v2 keeps one generated
menu/metadata commit including its request roots.

## Validation and limits

```sh
python3 -B docs/formats/draft-v1/check_workflows.py
```

Requires Python 3.11+, repository `tools/mpm_selection.py` (pure selector, no
provider calls) and jsonschema (checked with 4.26.0). It also runs the first
checker. Fixtures: six first-slice JSON plus fifteen workflow JSON examples,
one TOML configuration and one valid finite synthetic resolver catalog. Origin
scenarios cover independent interactive claims/override retention and removal
of configuration-only wishes. Record/claim/invocation IDs and metadata byte
bindings are recomputed. Negative cases cover source/provider rebinding,
cache/path damage, approval mismatch, scope expansion, cycles, unsupported
policies, bad boot bindings and missing recovery entries.

These are documentation fixtures, not installable packages, real approvals,
actual filesystems/capabilities or boot acceptance. External IDs/artifacts are
synthetic. Tests do not authenticate publishers, import payloads, mutate a
registry, execute a handler or start a VM. No extra manual VM round is needed.

Maps/views obey declared metadata/collection limits. Large catalog sharding/index
formats need explicit versioned coverage before whole large-provider exports
are claimed. Never truncate a view and call it complete. Existing provider
experiments remain separate until explicit metadata adoption.

Remaining gates: owner review; new Ports origin-state embedding/old-writer
refusal; native-v2 layout/reader transition and actual realization checks; build
recipe/workspace wire/provenance; actual handlers/acquisition/publishers; remote
trust/large-catalog indexing and physical rollout. This fills the requested
format slice, not every implementation/security boundary.
