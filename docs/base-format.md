# Mojt Base Release Format (prototype format 1)

A release is a directory containing:

```text
base-0.1.1-x86_64/
  rootfs.tar.zst
  rootfs.tar.zst.sha256
  manifest.toml
  packages.txt                  # optional build provenance
```

`format = 1` is **the manifest schema version**; it is not the Base version, image version, or state layout version. New formats must be explicitly supported by readers.

## Example manifest

```toml
format = 1

[base]
name = "mojt"
version = "0.1.1"
architecture = "x86_64"

[abi]
libc = "glibc"
libc_version = "2.41"

[image]
file = "rootfs.tar.zst"
sha256 = "<64 lowercase hexadecimal characters>"

[state]
layout_version = 1
etc_defaults = "/usr/etc"
etc_policy = "add-missing"
var_policy = "persistent"

[build]
backend = "void"
packages = "packages.txt"     # optional
```

`mojt-base-pack` writes the manifest, including the actual image SHA256. A checksum provides corruption detection, **not authenticity**. Signed release metadata is not yet implemented.

## Filesystem contract

- `/usr/lib/os-release`: generated by the packer; identifies Mojt and the active image version.
- `/usr/etc`: distribution-supplied configuration defaults.
- `/etc`, `/var`: empty directories in the image, mounted from persistent state at runtime.
- `/run`, `/tmp`: runtime or temporary data, not contents carried across a Base update.
- `/home`, `/root`, `/srv`, `/opt`, `/usr/local`: empty mount points in the prototype image; final persistence policies are still to be specified.

`mojt-base-install` preserves existing entries in persistent `/etc`, adds missing defaults, and does not delete them on rollback. It requires `/etc/os-release -> ../usr/lib/os-release` in the persistent state. It can switch a `base/current` symlink to an installed generation; it does not mount state automatically or change the root filesystem of a running process.

## Compatibility and safety

The current prototype accepts only the supported manifest schema and state layout and checks release architecture and image hash. It performs an archive safety audit before unpacking. This should not be treated as sufficient validation for untrusted releases: authenticated manifests, additional hardening, and boot-time integrity checks are still needed.

A Base switch must eventually be checked against the System and Ports ABI requirements. Returning to an older Base does not automatically roll back `/var` contents or service data formats.


## Installer failure contract (prototype)

For ordinary, catchable installation errors, the installer now attempts to remove
the newly published Base generation, newly copied release metadata, and all
newly created persistent-state entries from that invocation. Existing files
under persistent /etc and /var are not deliberately modified or removed.
Conflicting /etc/os-release and state layout markers are checked before
populating defaults. Activation is the last installation step.

This is **not** a crash-safe transaction: SIGKILL, power loss, disk failures
during rollback, concurrent edits outside the installer's lock, and durable
fsync/rename ordering are not covered. A failed rollback prints an error and
requires manual inspection. SHA256 still does not authenticate a release.

To run the synthetic failure regression tests without a built Base release
(on a Linux host with Python 3.11+, GNU tar, and zstd):

```sh
python3 -m unittest discover -s tests -p 'test_base_install_failures.py' -v
```

The existing privileged integration test remains
`tests/test-base-upgrade.sh` and should also pass unchanged.

## Durable publication and conservative recovery (prototype)

Installation now requests `fsync` for staged rootfs contents and directories
before publishing a Base generation, and publishes the release manifest by
temporary-file rename and directory `fsync`. Activation uses a temporary
symlink, `os.replace`, and a directory `fsync`. A generation without its
release metadata is rejected by `activate`.

Run `sudo tools/mojt-base-install recover --target TARGET` to clean up
recognizable interrupted `.install-*` **staging** directories. Only directories
with the expected `.mojt-install-stage` marker are removed. Published
generations missing metadata are **reported but never deleted automatically**;
inspect their contents and current symlink before removing anything. The
recovery command holds the installer's lock.

**Limits:** There is still no atomic transaction spanning rootfs publication,
manifest publication, and persistent `/etc`. A power failure can leave new
defaults or a published, incomplete generation behind. Recovery does not
undo such defaults or remove published generations. `fsync` improves
durability on filesystems that honor it, but this is not a power-cut-tested
guarantee. Never auto-delete state based only on installer markers. Release
authenticity and rollback of service data are separate future work.

## Base root directory ownership

The packer sets the **staged image root** (archive entry `./`) to numeric
UID/GID `0:0` and mode `0755` after copying the bootstrap tree.
GNU `cp -a SOURCE/.` otherwise propagates the bootstrap directory's host
ownership and permissions onto the stage root. Other packaged paths retain
their existing metadata. The original bootstrap tree is never modified.

This applies to **newly packed releases**, not previously published images.
Old Base releases must not be rewritten in place; create a new versioned
release to obtain the normalized root ownership.

Regression test (synthetic rootfs, **requires sudo**):

```sh
sudo python3 -m unittest discover -s tests -p 'test_base_pack_root.py' -v
```
