# Native artifact format v1: package prototype

Status: experimental packer/verifier, not an installer or production signed
repository. The [architecture manifesto](mpm-artifact-architecture.md) defines
the wider model. This increment packages frozen staging inputs for all four
kinds using Python 3.11+ and `zstd`; no Nix, network, compiler or root permission
is needed for the ordinary fixtures. Reading protected real inputs may require
their owner's permissions. No archive is extracted and no hook is executed.

## One category in every package

Every logical tar member is the category directory or a descendant of it.
The allowed category names are exactly `base`, `system`, `kernel`, `port`.
The CLI area's plural `ports` maps to the singular package kind `port`.

| Kind | Embedded descriptor | Payload example | Meaning |
| --- | --- | --- | --- |
| Base | `./base/artifact.json` | `./base/payload/rootfs.tar.zst` and `manifest.toml` | One existing complete Base release, wrapped without changing its image |
| System | `./system/artifact.json` | `./system/payload/bin/...` or a composition record | A component or a generation composition with exact runtime references |
| Kernel | `./kernel/artifact.json` | `./kernel/payload/boot/vmlinuz-RELEASE`, `lib/modules/RELEASE/...` | One kernel and its matching module/configuration set |
| Port | `./port/artifact.json` | `./port/payload/bin/...` | Native application files, with exact external references where needed |

Optional evidence files live under `./KIND/provenance/`. There are no package
files at the tar root outside that category, including the descriptor. Standard
PAX extension records represent long path/link names; they are tar transport
metadata rather than additional extracted files. The verifier checks logical
member names, types, order and contents, including rejection of a second category.

The prefix is an **archive namespace**, never an instruction to install
`/kernel/payload` or `/port` into the running root. A future area adapter maps
the verified payload into a private immutable destination. It must not run
`tar -xf PACKAGE -C /`. No transport metadata path is an installation target.

This does not relocate Nix binaries. External-provider runtime objects retain
their required paths and are referred to by explicit exact dependency records.
A System generation may be a small composition plus references instead of a
duplicate archive of its components. Packaging those references does not fetch
their closures or make them locally available. The prototype does not infer
dependencies, make a package standalone, or validate complete deployment ABI.

## Why the descriptor is inside and also outside

An exported package directory contains:

- `KIND-NAME-RELEASE-PLATFORM-IDPREFIX.tar.zst`, the complete single-file package.
- `artifact.json`, a byte-identical copy of `./KIND/artifact.json` in that file.
- `archive.json`, a transport record with filename, size, full archive SHA256
  and the exact artifact ID.

The package alone is inspectable/verifiable; the external copy lets a catalog
offer metadata without downloading the payload. The writer verifies the archive
before publishing the new output directory and never overwrites a prior output.
The 12-hex ID prefix in the filename is a convenience, not an authoritative
identity or collision guarantee. Readers use the full ID.

**Avoid the hash cycle:** the descriptor inventories payload/evidence entries
but not itself. Its ID hashes its canonical body with only the `id` field
omitted. It contains no archive checksum, mutable download URL, signature or
host staging path generated by the packer. The compressed archive hash is
outside, in the transport record/catalog. Another compression representation
can carry the same artifact ID; changing version metadata, dependencies,
provenance, contents, owner/mode or link relationships changes the artifact ID.

The detached transport record is not signed. Hashes detect changed content;
they do not establish publisher authenticity, current maintenance or freshness.
Production publication must bind the descriptor and transport under the
repository's separately specified trust/update policy.

## Versions and traceability

`version` has explicit `upstream`, `scheme`, `revision` and derived `release_id`.
The numeric scheme is `dotted-v1`; `opaque-v1` preserves nonnumeric names and
requires exact selection unless a future explicit comparison adapter is added.
Revision is either null or a nonnegative integer. A null revision preserves the
upstream string as the release ID; a numbered revision appends `-rN`, using
the existing `mojt-r-v1` convention rather than parsing arbitrary vendor suffixes.

| Example | Upstream | Package revision / release ID | Payload identity |
| --- | --- | --- | --- |
| Existing Base | `0.1.3` | null / `0.1.3` | Existing manifest and rootfs bytes preserved |
| Own kernel | `6.12.107` | 1 / `6.12.107-r1` | `kernel_release` remains `6.12.107-mojt1` |
| System label | `system-A` (opaque) | null / `system-A` | Exact component/composition ID |
| Native Port | `1.2.3` | 2 / `1.2.3-r2` | Exact native ID plus runtime references |

The kernel package's new distribution release ID does **not** rename the built
kernel, `uname` output, module directory, old `mojt-kernel-input-v1` ID or source
tag. Their relationship is explicit metadata. No heuristic translates a
`-mojt1` suffix into `-r1`. The new Kernel export command requires its package
revision explicitly. Base wrapping never edits the version inside its existing
manifest. Version/revision labels identify releases; exact descriptor IDs
identify builds. Multiple different IDs under one release remain ambiguous
without an explicit build preference, as in the existing resolver.

The Kernel adapter verifies the ready build record's ID, exact staged file map,
final and seed config hashes, config diff, source/version relationship and
recorded sampled vermagic. It retains the original `kernel.json`, `debian.config`
and `config.diff` byte-for-byte as evidence, records the old build ID and compiler
environment hash, and requires the expected image/config/map/module layout.
It does not rerun Kbuild/modinfo or independently prove that every module can
load. Existing boot acceptance remains separate evidence; its old build record
is not rewritten to claim a new test result.

## Descriptor and spec schemas

`mojt-artifact-spec-v1` is the packer's explicit input recipe. Required fields:
`format`, `kind`, `name`, `platform`, `version`, `dependencies`, `requirements`,
`provides`, `provenance`, `metadata`. Its version omits the derived `release_id`.
See the [Port fixture](../manifests/artifact-port-example.json). Platform/name/
release tokens are bounded and path-safe. Unknown fields/formats and duplicate
JSON keys fail; metadata has a 16-MiB limit. Empty objects/lists must be explicit,
not inferred discovery results.

`mojt-artifact-v1` adds `id`, `payload_layout` and `files`, replacing the input
format marker. All kinds use the same descriptor and tar container. Layout is
`base-release-v1` for existing Base release directories and `tree-v1` otherwise.
System metadata must state `system_role: component` or `generation`; Kernel
metadata must state its exact `kernel_release`. Other metadata, requirements,
provides and provenance are declarative JSON objects, not executable hooks or
yet a general capability solver.

Native dependencies are `{ "provider": "native", "artifact": "sha256:FULL_HEX" }`.
Other providers use `{ "provider": "NAME", "identity": { ... } }`; that identity
is opaque to the packer and must be verified by the declared adapter before
installation. No provider-name fallback or acquisition occurs here. Dependency
and provenance records are part of identity; download mirrors are not.

The `files` inventory records category-relative paths rooted at `payload` or
`provenance`: type, numeric uid/gid, permission bits, regular-file size/hash,
symlink target or an earlier regular-file hardlink target. The payload root's
owner/mode is recorded too. Directory ancestors must precede children; links
cannot be ancestors of another inventory member. The writer uses sorted
directory traversal. Descriptor order is bound by identity and tar order.

v1 canonical serialization is UTF-8-compatible ASCII JSON: dictionary keys
sorted by Unicode code point, ASCII escaping, separators `,` and `:`, no optional
whitespace. Only strings, integers, booleans, null, arrays and string-keyed
objects are allowed; floating-point/nonfinite numbers are rejected recursively.
The ID is `sha256:` plus lowercase hex SHA256 of this body without `id`.
The embedded/detached descriptor is the canonical full object plus one newline.
The newline is not part of the ID body. The old Kernel build ID retains its
own existing rules and is preserved, not reinterpreted as this package ID.

## Filesystem metadata boundary

The writer preserves numeric owners, permission bits (including setuid/setgid),
regular data, symbolic targets and hardlink relationships. It never follows a
symlink during inventory traversal. Absolute symlink targets can be legitimate
runtime paths and are recorded without reading their destinations; they are
not acquisition instructions. An installer must constrain extraction/link
handling and validate deployment/runtime references before activation.
The frozen staging tree's numeric ownership must already be intentional package
metadata; copying/chowning it changes the descriptor identity. The packer does
not silently turn the invoking user's ownership into another installation owner.

Archive timestamps are normalized to zero, owner/group names omitted, and
packing uses one-thread zstd level 3. Host staging paths and source mtimes do
not change identity. This improves deterministic packaging with the same tools
but does not establish reproducible source builds or cross-version compressor
identity. Mtime-dependent application data is outside this initial package scope.

**Explicit prototype limit:** raw-tree xattrs, POSIX ACLs/capabilities, device
nodes, FIFOs and sockets are rejected rather than silently dropped. Empty
directories, executable bits, links and numeric ownership are supported. A raw
Base rootfs or a Port requiring unsupported attributes needs a versioned
metadata extension before it can be packed directly. Existing Base archives
remain opaque bytes inside the wrapper, so their internal metadata is retained.
The Base adapter checks its existing manifest version and image hash without
unpacking/repacking the rootfs. It is not a replacement Base installer.

The streaming verifier compares the descriptor, every logical member and file
hash, link targets and numeric metadata; unexpected entries, traversal, a second
category, nonzero data after the tar end marker and zstd failures are rejected.
It never calls extract/extractall or writes archive contents to disk. Limits
are 200,000 inventory entries and 64 GiB declared regular data. This is not a
production denial-of-service-hardening or malicious publisher trust claim;
future acquisition/extraction remains a separate reviewed implementation.

## Commands and acceptance

Create a frozen source directory and edit an explicit spec, then:

```sh
python3 -I -B tools/mojt-artifact-pack.py pack \
  --source /FROZEN/PORT-TREE --spec manifests/artifact-port-example.json \
  --output /NEW/PACKAGE

python3 -I -B tools/mojt-artifact-pack.py kernel \
  --build /COMPLETED/KERNEL-BUILD --revision 1 --output /NEW/KERNEL-PACKAGE

python3 -I -B tools/mojt-artifact-pack.py verify /PACKAGE/EXACT-NAME.tar.zst \
  --expected-id sha256:FULL_DESCRIPTOR_ID

python3 -B -m unittest discover -s tests -p 'test_mojt_artifact.py' -v
```

The generic command accepts optional `--attachment NAME=FILE`. The Kernel
command also accepts attachments but cannot replace its mandatory build evidence.
All outputs must be new, outside the source tree. Packaging does not install,
select or activate anything, touch the running `/boot`/module tree, modify the
build result, rebuild a kernel, or publish a repository/catalog entry.

Automated fixtures perform real tar/zstd round trips for all four kinds, plus
a reference-based System generation, unchanged nested Base image metadata,
long/Unicode paths, symlink/hardlink/mode/owner preservation, deterministic
repacking and identity changes, corrupt/truncated/mixed archives, unsupported
attributes, Kernel build-evidence mismatch and isolated CLI operation without
provider code. These automated format tests are separate from the owner-run
real-kernel package acceptance below and the earlier kernel boot acceptance.

This accepts real native Kernel packaging and portable content verification.
It does not register an installed kernel, publish a catalog entry, validate a
new deployment or change boot selection. Real Base/System/Port exports remain
separate from their successful synthetic format fixtures. Repository trust,
production import/extraction and boot deployment remain separate work. The
first [local Kernel install/status prototype](mpm-kernel.md) now consumes this
accepted format with a conservative regular-file/directory subset. Another
kernel build or unrelated VM account/generation cycle is not required.
